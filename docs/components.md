# Component Design

English | [中文](components.zh.md)

> Concept definitions are in concepts.md §Component. This document specifies the call protocol, lifecycle events, direction geometry, rendering, and interaction event format.

## Call Protocol (call_component)

The pet initiates via the Tool Set; AmberyBackend forwards to the UI for rendering. **`call_component` manages the whole lifecycle (create/update/close)** — the same id creates on first call, updates in place on later calls, and closes explicitly.

The Tool schema declares the complete fields of each type via `anyOf` (all LLM providers support nested `anyOf`; `oneOf`/`const` are not needed). The top level of a spec carries only what applies to every type; everything type-specific lives in `content`:

```ts
// Direction names (consistent with docs/toolset.md; the engine resolves them on a 16-direction ring, see positioning/types.ts)
type Direction =
  | 'n' | 'ne' | 'e' | 'se'
  | 's' | 'sw' | 'w' | 'nw'
  | 'auto';

type ComponentSpec = {
  id: string;
  type: string;                 // a registered Component type (§Type registry)
  direction?: Direction;
  action?: 'close';
  content: object;              // shape owned by the type's registry entry
};

// The registered types and the content shape each owns:
type ComponentContent = {
  text_card:  { title: string; text: string };       // text is a markdown subset (§Rendering)
  quick_jump: { label: string; target: string };
  data_chart: { title: string; chart: { kind: 'line' | 'bar' | 'pie'; labels: string[];
                                         series: { name: string; data: number[] }[] } };
  todobox:    { title: string; items: { text: string; done: boolean }[] };
};
```

- `id` is generated by the pet (e.g. `cmp-001`); repeating a call with the same id = **update in place** (not a toggle close). Creation and update share the same spec structure.
- A type-specific field never appears at the top level: `content` is the only carrier for it, so a new type adds a registry entry rather than a new top-level parameter.
- `text_card.content.text` carries a markdown subset (§Rendering), not plain text.
- Closing a card: `action: "close"` (only `id` is needed; `content` is ignored). Two-level compatibility: if the LLM puts `action` at the top level of args (alongside `spec`), the backend also recognizes it as a close.
- When `direction` is omitted or `auto`, it is selected automatically by "the direction with the most remaining screen space".
- The text-volume constraints (see §Rendering) are system prompt constraints on the pet; the rendering layer does not hard-validate them.

## Type registry

A Component type is a registry entry, not a branch in the tool schema or in core. An entry owns:

| Part | Responsibility |
|---|---|
| `contentSchema` | the JSON Schema fragment for this type's `content`; the tool schema's `anyOf` is generated from these fragments |
| `validate(content)` | structural validation and its error message |
| `render(content)` | the Card body for this type |
| `sizeModel(content)` | how the type contributes to the Card window size: a block recipe, a fixed size, or a cap with scrolling (docs/card-window-size.md) |
| `label` / icon | the Cards Shelf row |

Adding a type means adding one entry. The call protocol, the top-level spec shape and the Card file shape do not change. `sizeModel` is mandatory — a type without one leaves the window size underivable, which the size contract forbids.

#### ⟡ Consistency Analysis

Component, Card, Surface, and OS Window are not concepts on the same layer: Component is structured content that the Agent can call; Card is the persistent object of that content as an ongoing work product; Surface is a logical interface that is visible, hideable, and restorable to the user; OS Window is the host's physical container, into which a Surface and a transient popup are both projected. Separating the four allows a Card to exist across restarts while window handles need not be persisted, and effects only audit actions without deriving the current Card from them. Chat and Cards are unified as Managed Surfaces (show/hide/restore semantics unified; they enter the engine's occupied area), and pet itself is a Managed Surface and the anchor — the origin the other Surfaces' offsets are measured from, with its visibility governing the group. The Cards Shelf is also not a Surface — it is a transient management popup anchored to the pet (same category as Menu: closes on focus loss, does not enter the engine's occupied area, has no persistent state); its source of truth is the managed `.card.json` collection.

A Card file is persisted as complete JSON: `component` is the Component spec that the Agent reads and updates normally; `_meta` is local Surface management state (schema version, creation time, display choice, and layout) and does not enter the Agent projection, nor is it overwritten by an ordinary same-id update. This way, after the user hides a Card, the Agent can still update its content but cannot silently overwrite the user's display choice through an ordinary update.

## Card File (.card.json)

One Card = one complete JSON file at `memory/cards/<id>.card.json` — content (`component`) and Surface state (`_meta`) colocated. The file is the Card's cross-restart truth: startup recovery reads from the file, not via effect.jsonl replay (action audit does not derive Cards backwards).

```json
{
  "component": { "id": "todo-1", "type": "todobox", "content": { "title": "清单", "items": [] } },
  "_meta": {
    "schema": 2,
    "created": 1785860000000,
    "user_closed": false,
    "layout": { "direction": "sse", "offset": [30, 40], "manual": true, "size": [480, 240], "layoutVersion": "9a3f2b1c" }
  }
}
```

- `component`: the Card's current content. The agent writes it through `call_component` (a same-id update replaces the whole component); a user interaction that changes content writes the updated content back into it. The file is therefore the single content source for rendering, for the size computation and for restart recovery.
- `_meta`: local Surface management state — does not enter the Agent projection (the tool result returns only ok/id) and is not overwritten by ordinary same-id updates:
  - `schema`: file format version (currently 2); a file written at version 1 keeps its type-specific fields at the top level of `component` and is migrated to version 2 — type-specific fields move under `content` — when it is loaded.
  - `created`: creation time (epoch ms); updates do not refresh it.
  - `user_closed`: display choice — user hide = true (Cards Shelf show/hide toggling writes via `set_card_user_closed`); Agent updates do not overwrite it.
  - `layout.direction`: spec.direction (`auto`/omitted = null; follows the spec on each update).
  - `layout.offset`: offset relative to the pet center (written back at the end of a user drag via the `update_card_layout` IPC; automatic layout = null).
  - `layout.manual`: the user has dragged it by hand = true (place keeps the offset without recomputing).
  - `layout.size`: projected Card window size `[width, height]` in CSS pixels, produced by the size computation; no user action edits it (docs/card-window-size.md).
  - `layout.layoutVersion`: identity of the inputs that determine `layout.size` (layout constants + font identity); a value that differs from the current inputs marks the projection stale.
- dismiss (agent close / user ×): ends the Surface — delete the file, leave the registry, forget the layout.
- id is the file-relative path: it may contain `/` (nested subdirectories); empty segments and `..` segments are forbidden (tool validation rejects them).
- Recovery: at startup, scan all `.card.json` under `memory/cards/` to rebuild the registry; bad files are skipped (one sick file does not take down the whole). Window rebuilding is pulled at pet startup (readonly `list_cards` IPC, returning component + `_meta`): cards with `user_closed=false` have their windows rebuilt; for `layout.manual`, the pet-relative offset is first seeded into the engine (`seedManual`), and a card's `requestPlace` hitting the manual occupied area restores it in place without occupying automatic layout. No push-at-startup — effect broadcasts sent before the webview is ready would be lost; pull has no timing hole.

## Card Lifecycle Events

Every card produces natural-language events during its lifecycle. Regardless of source (agent call / user action), events enter the Event Buffer and are attached into Context when the Queue admits them. Format:

| Event | Source | Natural language |
|---|---|---|
| `created` | agent | `card created: {type} "{title}" ({id}) @ {YYMMDD-HH:MM}, → alive N` |
| `closed_by_user` | user × | `User closed {type} "{title}" ({id})`<br>`card closed: {type} "{title}" ({id}), {start} / {end}, → alive N` (two lines) |
| `closed_by_agent` | agent | `card closed: {type} "{title}" ({id}), {start} / {end}, → alive N` (one line) |
| `user_action` | user interaction | `User{checked/unchecked/added} {type} item "{text}"` (per-item process) |

The frontend protocol for interaction events: the frontend only reports structured facts (action/cardId/field); the natural-language text is written on the fly by core in the Harness language through the lifecycle single source (docs/i18n.md §Harness internal language); this table is a Chinese semantic sample.

- Agent updates to a card produce no event (the tool result already carries the complete spec).
- `start` / `end` format: `YYMMDD-HH:MM`.
- `alive N` = the number of cards remaining after the event.

## Direction Geometry

- Anchor = View center. Cards offset along the direction vector: `anchor ± (View radius + 12px gap + half card size)`.
- Diagonal directions (e.g. top-right) offset each axis separately.
- Off-screen handling (docs/window-follow.md §Off-screen and overlap): not covering the person > fully visible; only when completely missing (zero intersection with its screen) does it retry by rotating around the 16-direction ring.
- Popped cards follow View movement via the engine using pet-relative offsets (docs/window-follow.md; user dragging can change the offset basis).

## Rendering

- Card structure: header (title + close button ×) + body (rendered by type).
- `data_chart` uses inline SVG (no dependencies): line=polyline, bar=rect, pie=path; hover details use the native SVG `<title>` tooltip.
- `text_card` renders its `text` as markdown: paragraphs, headings, ordered and unordered lists, blockquotes, fenced code blocks, tables, horizontal rules, and inline emphasis / strong / code / links. Images and raw inline HTML are not rendered — they appear as their source text — because an image's height is only knowable after it loads and raw HTML is the largest injection surface.
- A fenced code block scrolls horizontally instead of wrapping; a table wraps cell content at the Card's width cap and scrolls horizontally inside the Card when it is wider.
- Text-volume constraints for the four types (system prompt constraints on the pet; the rendering layer does not hard-validate):

| Type | Description | Text volume | Interaction |
|---|---|---|---|
| `text_card` | Title + markdown subset, basic information display | 200-500 characters | Copy/close |
| `quick_jump` | Quick jump | 50-100 characters | Click to jump |
| `data_chart` | Line/bar/pie chart | Title + legend 50 characters | Hover details |
| `todobox` | Todo list, checkable | 30-100 characters per item | Check/add |

## Interaction Events → Event Buffer

concepts §Component / §Event Buffer: user interactions **do not write the user role in Context, nor go through the Queue**; they are written into the Harness Event Buffer. Each record carries a two-part payload:

- **Natural language** (required): description of the operation process
- **Structured state snapshot** (optional): attached only for todobox-type interactions; deduplicated and merged into one final state for the same card within a single flush

An interaction that changes content — checking or adding a todobox item — also writes the updated content back into the Card file (§Card File). The Event Buffer record stays the audit trail of the action; the file stays the single content source.

The frontend reports via `bridge.pushEvent(desc, state?)`:

| Interaction | Natural language | Structured snapshot |
|---|---|---|
| Close | `User closed {type} "{title}" ({id})` + the lifecycle `card closed:` line | — |
| Copy (text_card) | `User copied the contents of text_card "{title}"` | — |
| Jump (quick_jump) | `User clicked quick_jump to jump to "{target}"` | — |
| Check/uncheck (todobox) | `User checked todobox item "{text}"` / `User unchecked todobox item "{text}"` | Deduplicated and merged per card: `{id, type, items: [{text, done}]}` |
| Add (todobox) | `User added todobox item "{text}"` | Same as above |

**Design decision**: hover details (data_chart) do not enter the Event Buffer — the interactions listed in concepts (close, jump, check) are all explicit actions; hover is too frequent and would flood the Buffer.

Jump actions (quick_jump → switch WT tab) only report an event before the C# sidecar is integrated; no real switch is performed.
